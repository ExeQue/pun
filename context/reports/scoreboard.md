### Release binary allocator (Linux, 2026-11-14)

The Linux release archives are static musl builds, and musl's allocator is slow when many threads allocate at once.
Decision: pun-cli uses mimalloc as the global allocator on musl targets, with `no_thp`, which halves its peak memory.
laravel-framework from `git archive`, 1681 files, the pun.toml v0.1.0's `pun migrate` writes; median of 3
`/usr/bin/time` runs (one for v0.1.0's `check`).

| command | v0.1.0 release (musl) | glibc build | musl + mimalloc |
|---|---:|---:|---:|
| `pun format --test` | 10.09 s, 50 MB | | 1.63 s, 89 MB |
| `pun check --test` | 134.24 s, 450 MB | 10.89 s, 535 MB | 12.84 s, 514 MB |

On Pinkary's packages, `pun update --no-install` takes 10.0 s with musl's allocator, 2.05 s with glibc's and 1.8 s
with mimalloc.

- Mago wins both rows on time and memory. Pun's cold lint runs about 450 Rector-mapped rules, many of them type-aware;

- Memory floor is the project scan. On laravel-framework RSS is 210 MB before it, 600 MB after the project's own files,

  Matching Mago would need type-aware rules without a codebase, which Rector parity does not allow.

  file, and about 40 s is the rules.
- macOS only: Mago's `mago-database` depends on `notify`, which links CoreFoundation and CoreServices into every
  binary (about 1.0 ms and 4.1 MB per run). `pun` needs `notify` for `--watch`, so it stays.
