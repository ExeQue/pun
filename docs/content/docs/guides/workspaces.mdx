---
title: Workspaces
description: Keep several packages in one repository with one lock and one vendor/.
---

A workspace is several packages in one repository. They share one `composer.lock` and one `vendor/` at the root.

## Create a workspace

1. In the root `pun.toml`, list the member directories or globs:

   ```toml pun.toml
   [workspace]
   members = ["packages/*", "apps/*"]
   ```

2. Give each member a `composer.json` with a `name`:

   ```json packages/billing/composer.json
   {
       "name": "acme/billing",
       "require": {
           "acme/core": "*"
       }
   }
   ```

3. Run `pun install`.

## How it works

- Pun requires every member at the root and symlinks it into `vendor/` as a path package.
- A member requires another member like any package, with `*` or any constraint.
- The root's own requirements and repositories go in the root `composer.json`. The root doesn't need one.

## Member rules

- `*` and `?` in a glob match within one directory name.
- Directories without a `composer.json` are skipped.
- A glob that matches nothing, such as `apps/*` before `apps/` exists, adds no member.
- A member without a `name` is an error.
- Two members can't share a name.

## Work in a member

`pun install`, `pun update`, `pun require` and `pun remove` find the workspace from the current directory. They always read and write the root `composer.lock` and `vendor/`.

`pun require` and `pun remove` edit the `composer.json` of the member you are in, or the root's at the root. Use `-p` for another member:

```bash
pun require -p acme/billing guzzlehttp/guzzle
pun remove -p acme/billing guzzlehttp/guzzle
```

If a request doesn't resolve, `composer.json` and the lock stay unchanged.

## Limits

- `pun install` doesn't notice a member's requirements changing outside `pun require` and `pun remove`. After you edit a member's `composer.json` by hand, run `pun update <member>`.
